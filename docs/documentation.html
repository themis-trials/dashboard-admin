Structure de référence : les fichiers sont ajoutés au fur et à mesure des besoins réels de chaque outil.

Les dossiers principaux

docs/ — Documentation

Contient la documentation générale du projet : arborescence, conventions de nommage, organisation du code, procédures de développement, tests, publication et maintenance. Elle sert de référence pour retrouver les décisions prises et les méthodes utilisées.

tools/ — Outils

Contient un sous-dossier par fonctionnalité du projet. Chaque outil regroupe ses fichiers principaux : interface, styles, logique JavaScript et, si nécessaire, documentation spécifique.

Par exemple, tools/rp-generator/ regroupe les fichiers propres au générateur de RP. Cette organisation permet de travailler sur un outil sans avoir à rechercher ses fichiers dans plusieurs dossiers génériques.

Un fichier ne doit être placé dans le dossier d'un outil que s'il lui appartient spécifiquement. Les fonctions réutilisées par plusieurs outils sont placées dans shared/.

shared/ — Ressources communes

Regroupe les ressources utilisées par plusieurs outils. L'objectif est de centraliser les éléments communs afin d'éviter de maintenir plusieurs copies d'un même code.

  • shared/scss/ : variables de thème, mixins, fonctions SCSS et styles de base communs.
  • shared/js/ : fonctions utilitaires JavaScript génériques et réutilisables.

Une fonction qui ne sert qu'à un seul outil reste dans cet outil. Elle ne devient une ressource commune que lorsqu'elle est réellement réutilisée ou qu'une mutualisation est justifiée.

server/ — Code serveur

Contient le code PHP exécuté côté serveur, notamment sur l'hébergement Infomaniak. Il centralise les traitements qui ne doivent pas être exécutés directement dans le navigateur et les ressources auxquelles plusieurs outils peuvent accéder.

  • server/api/ : points d'entrée permettant aux interfaces de demander des données ou de déclencher des traitements serveur.
  • server/config/ : paramètres de configuration et correspondances nécessaires au fonctionnement du projet.
  • server/includes/ : fonctions PHP communes, vérifications, authentification et autres traitements réutilisables.
  • server/data/ : fichiers de données utilisés par le serveur, par exemple des fichiers JSON.

Les données sensibles et les secrets de configuration ne doivent pas être exposés dans le code envoyé au navigateur ni publiés dans un dépôt Git accessible publiquement.

environments/ — Environnements

Regroupe les adaptations nécessaires au fonctionnement des outils selon la plateforme utilisée. L'objectif est de conserver une logique commune lorsque c'est possible, tout en isolant les contraintes propres à chaque environnement.

  • environments/local/ : éléments spécifiques à l'exécution et aux tests en local.
  • environments/forumactif/ : scripts, adaptations et intégrations nécessaires au fonctionnement sur le forum Forumactif.

Ces dossiers ne doivent pas devenir une seconde copie complète de chaque outil. Ils accueillent uniquement les éléments qui diffèrent selon la plateforme ou qui ne peuvent pas être mutualisés directement.

.gitignore — Fichiers exclus de Git

Définit les fichiers et dossiers que Git ne doit pas suivre, par exemple certains fichiers temporaires, journaux, configurations locales ou secrets. Il doit être adapté au projet et ne remplace pas une gestion sécurisée des données sensibles.

Organisation des fichiers d'un outil

Les noms de fichiers ci-dessous constituent une convention de départ. Tous les outils ne sont pas obligés de posséder exactement les mêmes fichiers.

EXEMPLE — GÉNÉRATEUR DE RP FICHIERS 
tools/rp-generator/
├── index.php
├── style.scss
├── script.js
└── README.md
  • index.php : structure de la page et génération éventuelle du HTML côté serveur. Pour un outil purement statique, un fichier index.html peut suffire.
  • style.scss : styles propres à l'outil. Il importe les variables, mixins et autres ressources communes dont il a besoin.
  • script.js : logique JavaScript propre à l'outil : interactions, événements, traitement des entrées et affichage des résultats.
  • README.md : notes techniques propres à l'outil : objectif, dépendances, fonctionnement particulier, points de vigilance et procédure de mise à jour.

Règles de partage du code

Le code est mutualisé lorsqu'il peut réellement être utilisé dans plusieurs contextes sans créer de dépendance inutile. La mutualisation ne doit pas rendre les outils plus difficiles à comprendre ou à déboguer.

  • SCSS : les variables, mixins et styles communs sont centralisés dans shared/scss/. Chaque outil conserve son propre fichier SCSS et importe les ressources nécessaires.
  • JavaScript : les fonctions génériques peuvent être centralisées dans shared/js/. Les règles métier et les interactions propres à un outil restent dans son dossier.
  • PHP : les fonctions serveur communes sont placées dans server/includes/, tandis que les points d'entrée des API sont rangés dans server/api/.
  • Environnements : la logique métier commune doit être séparée des adaptations nécessaires au navigateur local ou à Forumactif.

Points de vigilance

  • Ne pas créer un fichier ou un dossier simplement pour remplir l'arborescence : il doit répondre à un besoin concret.
  • Ne pas dupliquer une fonction dans plusieurs outils si elle peut être partagée sans complexité excessive.
  • Ne pas déplacer du code dans shared/ uniquement parce qu'il ressemble à du code commun : vérifier d'abord qu'il possède le même rôle et le même comportement dans les différents outils.
  • Vérifier les chemins d'importation après tout déplacement de fichier, notamment les imports SCSS, les scripts JavaScript et les appels aux API.
  • Les scripts destinés à Forumactif peuvent être soumis à des contraintes d'intégration différentes de celles d'une page locale. Un module JavaScript partagé ne peut pas nécessairement être importé directement depuis le forum. Il faut donc définir une méthode fiable de distribution ou de synchronisation.
  • Distinguer le code source des fichiers générés, compilés ou déployés. Par exemple, le SCSS est le fichier source des styles, tandis que le CSS compilé est le fichier chargé par la page.

Principe général : chaque fichier doit avoir un emplacement évident, une responsabilité identifiable et une seule source de vérité lorsque son contenu est partagé. L'arborescence doit évoluer avec les besoins réels du projet, et non l'inverse.

04 — CONVENTIONS

Des règles simples, toujours les mêmes.

04

Des conventions communes permettent de garder un code lisible, cohérent et facile à maintenir. Elles s'appliquent à tous les outils, sauf contrainte technique particulière.

ÉLÉMENT CONVENTION EXEMPLE
Fichiers et dossiers Minuscules, mots séparés par des tirets rp-generator.js
Blocs CSS Nom représentant un composant ou une zone autonome .tool-card
Éléments CSS Deux underscores __ entre le bloc et son élément .tool-card__title
Variantes CSS Deux tirets -- entre le bloc et sa variante .tool-card--featured
États CSS Classe explicite décrivant l'état .is-active
Attributs JavaScript Attributs data-* pour cibler ou configurer un élément data-tool
Variables et fonctions JS camelCase getPokemonName()
Constantes JS UPPER_SNAKE_CASE pour les constantes globales ou de configuration API_URL
Variables SCSS Préfixe $, noms en minuscules avec tirets $color-primary
Mixins SCSS camelCase ou noms avec tirets, selon une convention unique dans le projet @include flex-center;

Nomenclature BEM

Les classes CSS suivent la convention BEM : un bloc autonome, des éléments rattachés à ce bloc avec __ et des variantes identifiées avec --.

EXEMPLE — COMPOSANT HTML / CSS 
<article class="tool-card tool-card--featured">
  <h2 class="tool-card__title">Générateur de RP</h2>
  <p class="tool-card__description">Description de l'outil</p>
</article>

.tool-card = bloc · .tool-card__title = élément · .tool-card--featured = variante

Règles d'utilisation

  • Utiliser des noms explicites et cohérents avec le rôle de l'élément.
  • Réserver __ aux éléments appartenant à un bloc BEM ; ne pas l'utiliser comme séparateur générique.
  • Utiliser -- pour une variante visuelle ou fonctionnelle d'un bloc, et non pour un état temporaire.
  • Préférer des classes d'état explicites comme .is-active ou .is-disabled lorsque l'état est géré dynamiquement.
  • Utiliser les attributs data-* pour les besoins JavaScript, plutôt que de dépendre d'une classe purement visuelle.
  • Garder la même convention de nommage dans tous les outils et éviter les abréviations difficiles à comprendre.

05 — COMMENTAIRES

Structurer le code sans le surcharger.

05

Les commentaires permettent de structurer les fichiers, de repérer rapidement les grandes parties du code et d'expliquer les comportements qui nécessitent un contexte supplémentaire. Une nomenclature commune facilite la lecture et la maintenance de tous les outils.

SYNTAXE UTILISATION EXEMPLE
En-tête de fichier Identifier le projet et le rôle du fichier // THEMIS TRIALS — GÉNÉRATEUR RP
// = Introduire une grande section fonctionnelle // = Configuration.
// > Introduire un sous-bloc ou une étape dans une section // > Récupération des données.
// Ajouter une explication ponctuelle au code // Vérifie que l'élément existe.
Commentaire de fin Préciser la fermeture d'un bloc lorsque cela améliore la lisibilité // = Fin de l'initialisation.

Nomenclature des sections

Les grandes sections sont introduites avec // =. Elles sont séparées du code par une ligne vide et portent un intitulé court décrivant leur rôle.

EXEMPLE — SECTION JavaScript 
// = Configuration.
const API_URL = "../api/rp_api.php";
const MAX_RESULTS = 10;


// = Éléments du DOM.
const form = document.querySelector("#rp-form");
const resultContainer = document.querySelector("#rp-result");


// = Initialisation.
function init()  {
  if (!form) return;

  form.addEventListener("submit", handleSubmit);
}

// = permet de repérer les grandes parties d'un fichier en un coup d'œil.

Nomenclature des sous-blocs

Le commentaire // > permet de subdiviser une section en plusieurs étapes ou sous-parties, sans créer de nouvelle grande section.

EXEMPLE — SOUS-BLOCS JavaScript 
// = Gestion du formulaire.

// > Récupération des données.
function getFormData() {
  return new FormData(form);
}

// > Validation.
function validateForm(data) {
  return data.has("pokemon");
}

// > Soumission.
function handleSubmit(event) {
  event.preventDefault();

  const data = getFormData();

  if (!validateForm(data)) return;

  // Envoie les données après validation.
  submitForm(data);
}

// > sert à organiser les étapes d'une même section, sans multiplier les séparateurs principaux.

Commentaires ponctuels

Les commentaires simples // sont réservés aux explications utiles à la compréhension du code. Ils peuvent préciser une contrainte technique, un comportement particulier ou la raison d'un choix d'implémentation.

EXEMPLE — EXPLICATION JavaScript 
function getPokemonSprite(pokemon, isShiny) {
  // Utilise le sprite shiny uniquement s'il est disponible.
  return isShiny && pokemon.shiny
    ? pokemon.shiny
    : pokemon.sprite;
}

Le commentaire explique la condition métier plutôt que de répéter le fonctionnement de l'instruction.

Règles d'utilisation

  • Utiliser // = pour les grandes sections fonctionnelles d'un fichier.
  • Utiliser // > pour les sous-blocs ou les étapes d'une même section.
  • Utiliser les commentaires simples // pour apporter une explication ponctuelle.
  • Privilégier des intitulés courts, descriptifs et terminés par un point.
  • Conserver une ligne vide entre un commentaire de section et le code qui le suit.
  • Ne pas commenter systématiquement chaque fonction ou instruction lorsque son rôle est évident.
  • Expliquer pourquoi un comportement existe ou pourquoi une solution est utilisée, plutôt que paraphraser le code.
  • Mettre à jour ou supprimer les commentaires lorsqu'ils ne correspondent plus au code.
  • Conserver cette nomenclature dans les fichiers JavaScript, PHP et SCSS.

  • Code : fichier complet ou extrait suffisamment large pour comprendre les fonctions appelées.

  • JavaScript : événements, fonctions appelées, éléments HTML concernés et messages de console.
  • PHP / API : point d'entrée, fonctions appelées, format des données et erreur serveur éventuelle.
  • Forumactif : emplacement d'installation du script, contraintes de la plateforme et résultat attendu.
  • Reprise de conversation : résumé des décisions, état du code et prochaine étape.

Règle de référence

Les prompts facilitent le travail, mais le code actuel et la documentation du projet restent les références. En cas de contradiction, vérifier l'architecture réelle et les dernières décisions avant de modifier le code.
